## What 1.0 means

A researcher who has never heard of Infall downloads it, opens it without a security warning, puts a real project into it, loses nothing, and can bring their lab in later. Concretely, 1.0 is reached when every line below is true:

1. Installers for macOS, Windows and Ubuntu open without a warning and update themselves.
2. Every feature has been seen working in the packaged app on all three systems, not only in tests.
3. A Local Workspace can be moved onto a team's server.
4. A slip on the Board or a Page is undone with Cmd/Ctrl+Z.
5. A Board of 2 000 Cards and a Page of 50 screens stay usable.
6. Someone who is not us has installed a Team server from the docs alone.
7. Three researchers have used it on real work for two weeks, and what stopped them is fixed.
8. The screens built without a designer have been through the design pass and approved.

## Where we are

Built: Board, Cards, Frames, Connections, Pages, Sources, Visuals, Runs and the Runner, Branches, Merge, History and Restore, To-dos, AI sidebar and Suggestions, Guests, Team server, desktop app with the server inside it, Local Workspaces, Presets, the hands-on Tutorial, the Tour, Settings, Workspace files and backups, Markdown/BibTeX export, BibTeX import, Look up.

Facts checked today that shape the plan:

- **No undo on the Board.** There is no Cmd/Ctrl+Z handling outside text fields. History and Restore exist but are too heavy for a slip.
- **No updater**, no code signing, no licence file.
- **The repository has no remote.** The only copy of the code is this computer.
- Windows and Linux have not been built or run since M11. The `.exe` and `.deb` files in `dist/` are stale.
- M12's later parts and all of M13 were verified by tests and, on macOS, partly by hand; most of their screens have not been seen in the packaged app.
- Known small defects: the window scrolls sideways at interface scale 150 % in a 900 px window; all Local Workspaces share one session cookie; a hand copy of a Workspace's database cannot be imported; exported BibTeX titles lose case protection.

## How the work is run

Same as M12 and M13: the owner decides, Fable writes the spec with contracts and zones and reviews, Opus agents build one zone each, everything is checked in the packaged app before it is called done. Each milestone ends with: all suites green, a build on every platform in scope, a hand check against a written list, one commit.

Two standing rules from here on:

- **Every milestone is run in the packaged app on its target platforms before the next one starts.** No more milestones verified by tests alone.
- **Nothing is called done by an agent's report.** Fable runs the suites and looks at the screen.

## The milestones

Order matters where it says "needs". Sizes are in working sessions like the ones so far, not calendar days.

### M14 — Solid ground (1 session; start now)

Nothing new; make what exists true.

- Push the repository to a private remote. *Owner: create it and give the address.*
- Hand check of M12 and M13 in the macOS app against `docs/specs/release.md` §8: Settings and the three scales, drag at 150 %, Export…, Import a workspace…, Show in folder, Print…, Markdown, BibTeX in and out, Look up against the real Crossref and arXiv. *Owner: ten minutes at a normal desktop, or approve screen control for Fable.*
- Fix the four known defects above. Add a rescue path: importing a raw `workspace.sqlite` with a clear warning.
- Delete the stale installers from `dist/`.
- Choose a licence and add it. *Owner decides: open source (which) or not.*

Done when: the checklist is ticked with nothing failing, the code is off this computer.

### M15 — Undo, and the Board at size (1–2 sessions)

- Cmd/Ctrl+Z and Shift+Cmd/Ctrl+Z on the Board and in Pages: undo the person's own recent Changes on this Branch, as new Changes (History stays honest), never someone else's. Needs a short grilling first: how far back, what happens when someone else changed the same thing since.
- A generator for large Workspaces (2 000 Cards, 6 000 Connections, 200 Pages, 50 000 Changes) and a measured pass: opening time, pan and zoom frame rate, search, History, Merge, export, backup. Fix what falls below "usable"; the likely work is drawing only what is on screen and paging History.
- A test that fails when these numbers regress.

Done when: the numbers are written down and acceptable on a five-year-old laptop; undo works for every kind of Board and Page edit.

### M15b — The Branch Graph (2 sessions; needs M15; grilled 2026-11-24)

Spec: [docs/specs/branch-graph.md](../specs/branch-graph.md).

- The Branches screen becomes the Branch Graph: every Branch from the first Change, one row per Activity, forks and Merges drawn, Checkpoints marked.
- A new Branch starts from any Activity or Checkpoint on any Branch, chosen on the graph; "from now" stays name + Enter.
- From a dot: preview the Board there, add a Checkpoint there, see every Change.
- One light server call for the whole shape; summary text only for rows on screen. Measured against M15's 50 000-Change Workspace.

Done when: the spec's hand check passes in the packaged app and the graph holds M15's numbers. Its look is settled in M17.

### M16 — Windows and Ubuntu, for real (1–2 sessions; needs a Windows machine)

- Build and package on both. Run the release checklist on a real Windows 10/11 machine and on Ubuntu 22.04/24.04 — not only in a container.
- Fix what breaks: webview differences (WebView2, WebKitGTK), paths, the Runner finding Python, printing, file dialogs, the port and firewall prompt on Windows.
- Continuous builds for all three systems on every push, so a platform never rots again. Needs the remote from M14.

*Owner: access to a Windows machine (yours, the friend's with a screen share, or a cloud one).*

Done when: the friend who could not start it opens a Tutorial Workspace on his computer.

### M17 — The design pass (2 sessions; can run beside M15 and M16)

- Owner runs the Claude Design prompt (already written), chooses directions for the start screen and the Tutorial, approves each screen. The prompt needs one addition: the M13 controls (row menu, Import BibTeX dialog, Look up, Page tools, print layout).
- Agents implement the approved designs as changes to tokens and components, screen by screen, each compared against the design at both themes and at the smallest window.
- Accessibility pass with a real screen reader (VoiceOver, NVDA) on the main paths.

*Owner: this one is mostly your time — choosing and approving.*

Done when: every screen on the list in the prompt is approved by you in the packaged app.

### M18 — From alone to a team (2 sessions; needs a grilling)

- Moving a Local Workspace onto a Team server: the Admin of a new or empty server takes in a Workspace file; the Local Member becomes a Member there; History, Branches, Checkpoints and To-dos arrive whole. Decisions to make first: empty servers only or merging into an existing Workspace (recommend: empty only for 1.0); what happens to the local copy afterwards; who the Changes belong to.
- The reverse — taking a Team Workspace home as a Workspace file — at least for an Admin, so leaving a server is always possible.
- The Team server install, tried cold: one command or one container, backups on by default, an upgrade path between versions with a schema migration test from every released version. *Someone who is not us follows the docs; we watch.*
- Comments on Cards and Pages with mentions, if the grilling says teams need it for 1.0 (recommend: yes, small — a thread per Card, outside versioning like To-dos).
- Changes stored append-only. Found in M15's measurement ([scale.md](../specs/scale.md)): every edit rewrites the whole Workspace in the database — 60–115 ms per edit on the 50 000-Change Workspace, growing with history, and other requests queue behind it. A table of Changes appended to instead fixes it; it is a schema change with a migration, so it belongs here with M18's other schema work and its migration test.

Done when: a project started alone is being edited by two people on a server an outsider installed.

### M19 — Sources a researcher expects (1–2 sessions)

- A PDF attached to a Source: stored with the Workspace (and in the Workspace file), opened inside Infall, searchable text. Annotation waits for after 1.0. Decisions: size limits, whether PDFs are versioned (recommend: no — stored once by content, referenced from Sources).
- The Board as an image and as SVG.
- A Python environment per Run (the Runner already picks an interpreter; add per-Workspace and per-Run choice and record package versions with the captured output).

Done when: a literature review with thirty PDFs lives entirely in Infall and exports whole.

### M19b — Runs in more than Python (2 sessions; needs M16 and M19; added 2026-11-24)

Spec: [desktop.md, "Languages — Runs in more than Python"](../specs/desktop.md) and [api.md §15, "Languages"](../specs/api.md).

- A Run names its language (`lang`, unset means Python); each Member sets up on their own device what that name starts — a Toolchain. The page never chooses a program.
- Built in: Python as it is, and Q# through the `qsharp` package of the chosen Python. Presets for Julia, R, JavaScript and Shell; any other language by hand.
- The approval window names the language and the command, and an approval is remembered per language.
- Before any zone starts: run the `qsharp` package by hand and settle the three points the spec lists under "To check when building"; correct the spec if they turn out otherwise.
- Zones: server and web library (the field, the result); the Runner crate (Toolchains, execution, approvals); the app's two windows (settings, approval); the Run block on the Page.

Done when: a Q# Run and a Julia Run are executed, stopped and re-read in the packaged app on all three systems; a Run sent as another language than it was approved in asks again; an app from before this milestone refuses a Julia Run instead of running it as Python.

### M20 — Shippable (1–2 sessions; needs accounts and money)

- macOS: Developer ID signing and notarisation. Windows: a code-signing certificate. Ubuntu: a signed apt repository or a signed AppImage. *Owner: Apple Developer Program (about $99 a year) and a Windows certificate (about $200–400 a year, or Azure Trusted Signing); these take days to be approved, so start them during M16.*
- Updates: the app checks a signed feed, says a new version is there, installs it on restart. Workspaces are backed up before the first start of a new version.
- Opt-in crash and problem reports with nothing from the Workspace in them.
- A download page, a changelog, version numbers that mean something (`0.9.0` for the beta).

Done when: a fresh download on each system opens with no warning and updates itself to the next build.

### Beta — real work (2 weeks of calendar time, little of ours)

- `0.9.0` to three researchers from different fields, each moving one real project in. *Owner: find them; ideally one works alone, one in a lab, one teaches.*
- We watch the first twenty minutes of each (screen share), then leave them alone, then ask after one and two weeks: what stopped you, what did you work around, what would make you move the next project in.
- A fixed channel for problems; every report gets an answer in a day.

### M21 — What the beta found (1–3 sessions; unknown by nature)

- Fix what stopped people. Refuse new features unless two of three asked for the same one.
- Final pass of the release checklist on all three systems, docs brought up to date, the Tutorial re-run from a clean install.
- Tag `1.0.0`.

## What could change this plan

- **Undo** may be harder than a session if "undo only my own Changes" conflicts with how Changes are recorded; the grilling in M15 settles it.
- **Scale**: if 2 000 Cards needs the Board redrawn differently, M15 grows.
- **Windows**: unknown until it runs; the original failure was there.
- **Q#**: the spec's Q# part is written from the `qsharp` package's documentation, not from running it. If the package behaves otherwise, that part of M19b is rewritten; the rest of the milestone does not depend on it.
- **The beta**: by design. If all three stop at the same wall, that wall is M21, whatever it is.

## After 1.0 — first in line

### Research routes as Suggestions

Today an AI can propose only a Source or a Connection. This lets it propose where the research could go next: a hypothesis, an open question, a next experiment — and a whole route (a few Cards with their Connections, in a Frame) — for a Member to accept or reject.

- **New kinds of Suggestion**: a Card, and a route (a Frame with a few Cards and Connections). Each carries its reason and what it rests on: the Cards, Sources and PDF pages it was drawn from, so a Member can judge it.
- **Asking for them**: an action on the Board or on a Frame ("Suggest directions") — the AI reads that part of the Research Content and answers with three to five routes as pending Suggestions.
- **Accepting**: puts the route on the Board, by default on a new Branch so that main stays as it is. Rejecting drops it. As with every Suggestion, nothing becomes Research Content until a Member accepts it.
- **No new model plumbing**: it goes through the existing tool layer and the Member's own subscription (ADR 0003).

Needs a grilling before a spec: what a route is in CONTEXT.md's words (the glossary's Suggestion is "a Source or Connection" and must be widened); where an accepted route lands; how many at once; how it is kept from repeating what is already on the Board. About one milestone: the tool layer and the accept ops (`crates/**`), the Suggestions panel and the Board action (`web/**`), the instructions the AI is given.
